## 1. この文書の目的

社内の複数アプリで共通に使えるCI/CD基盤について、**何を作るのか**を定義する。
どう作るかは[設計書](design.md)、なぜその判断をしたかは[ADR](adr/)に分ける。

想定読者は、この基盤を使うアプリチーム、基盤を運用するプラットフォームチーム、
および承認ゲートに関わる承認者。

---

## 2. 背景と課題

社内には複数のサービスがあり、各サービスは複数のアプリを持つ。
現状、CI/CDは各アプリチームが個別に構築している。

これにより次の問題が起きている（本基盤が解決しようとする課題）。

| # | 課題 |
|---|---|
| C-01 | **チームごとにデプロイの精度がばらつく。** 検査の有無、検査基準、デプロイ手順、承認の有無がチームごとに異なる |
| C-02 | 新しいアプリを立ち上げるたびにCI/CDを作り直している |
| C-03 | リリースの記録がチームごとに異なる形で残っており、横断的に追えない |
| C-04 | セキュリティ検査の基準がチームに委ねられており、厳しいチームと緩いチームが生まれる |

---

## 3. 目的と非目的

### 3.1 目的（ゴール）

**G-01: アプリチーム間のデプロイ精度のバラツキをなくす。**

これが唯一の主目的である。以下の判断はすべてこの目的に照らして行う。

バラツキをなくす手段として、次の考え方を採る。

> **アプリ側が処理を書けない（書かなくていい）構造にする。**
> 各チームがCI/CDを自由に書ける状態では、書き方の差がそのまま精度の差になる。
> アプリ側の記述を宣言だけに絞れば、実装差が生まれる余地がなくなる。

**G-02: 新しいアプリの立ち上げコストを下げる。**（G-01の副産物）

**G-03: リリースの記録を横断的に追える状態にする。**

### 3.2 非目的（やらないこと）

| # | 非目的 | 理由 |
|---|---|---|
| NG-01 | 環境間の差分をゼロにすること | 環境ごとに設定が違うのは当然。問題は**チーム間**の差 |
| NG-02 | デプロイ頻度を上げること | 承認ゲートを要件とするため、頻度はむしろ下がる |
| NG-03 | 既存アプリの全面移行 | 実験フェーズではサンプルアプリで検証する |
| NG-04 | チケット管理ツールの実装 | 擬似チケットで代替する。実務では既存ツールと連携 |

## 4. 用語定義

認識の齟齬が起きやすい用語を明示的に定義する。

### 4.1 環境

| 環境 | 定義 | 誰のものか | 昇格チェーン |
|---|---|---|---|
| **dev** | **開発者が自由にデプロイして動作確認するサンドボックス。** 任意のブランチを任意のタイミングでデプロイできる。状態は常に誰かの作業中コードであり、「正しい状態」は定義されない | 開発者全員（共有のスクラッチ領域） | **含まれない** |
| **stage** | **リリース前の確認環境。** 本番に出す予定の成果物を、本番に近い構成で確認する | リリース判断を行う人（QA / PO） | 含まれる（起点） |
| **prod** | **本番環境。** 実利用者が使う | 運用（SRE） | 含まれる（終点） |

**devが昇格チェーンに含まれないことが重要。** devはサンドボックスなので、
そこで動いたことはprodで動くことの根拠にならない。根拠になるのはstageでの確認である。

### 4.2 その他

| 用語 | 定義 |
|---|---|
| **昇格（promote）** | ある環境で確認した**同一の成果物**を次の環境へ適用すること。ビルドし直さない |
| **成果物** | コンテナイメージ（ECSの場合）またはzip（Lambdaの場合）。識別子は image digest または source hash |
| **リリース** | stage または prod へのデプロイ。「出す判断」を伴う人間の操作が起点 |
| **デプロイ** | ある環境にリソースを適用すること。devへのデプロイはリリースではない |
| **ゲート** | CI/CDを停止させる判定。セキュリティゲート（検査結果による）と承認ゲート（人間による）がある |
| **ペルソナ** | 承認者の役割（開発リード / QA・PO / SRE）。実アカウントとは分離して定義する |
| **擬似チケットツール** | 実験用にDynamoDBで表現したチケット管理の代替 |

## 5. ステークホルダー

| 役割 | 関心事 | 本基盤との関わり |
|---|---|---|
| アプリ開発者 | 早く確認したい。CI/CDを書きたくない | devへ自由にデプロイ。宣言ファイルのみ記述 |
| 開発リード（`dev_lead`） | 変更内容の妥当性 | stage承認、prod 1段目承認 |
| QA / PO（`qa_po`） | リリースしてよいか | prod 2段目承認 |
| SRE（`sre`） | リリース時間帯、影響範囲、切り戻し | prod 3段目承認、緊急リリース承認 |
| プラットフォームチーム | 基盤の保守、基準の一元管理 | `platform-cicd` / `platform-infra` を所有 |
| 監査 | 誰がいつ何を承認し、何を出したか | リリース記録、レポート、実行ログ |

## 7. 機能要件

### 7.1 共通CI/CDの提供

| ID | 要件 | 優先度 | 関連ADR |
|---|---|---|---|
| FR-01 | CI/CDの実装を中央リポジトリに集約し、各アプリリポジトリから再利用可能ワークフローとして呼び出せること | 必須 | [0001](adr/0001-repository-topology.md) |

## 9. 制約

| ID | 制約 | 影響 |
|---|---|---|
| CON-01 | GitHub Free plan | privateリポジトリでは承認ゲートが使えない → publicを選択（ADR-0002） |
| CON-02 | publicリポジトリ | 機密をリポジトリ・ログ・Artifactに置けない。ログとArtifactは誰でも閲覧可 |
| CON-03 | 使えるGitHubアカウントが1個 | 「別人が承認する」の検証ができない。自己承認禁止をOFFにする必要がある |
| CON-04 | AWSアカウントが1個 | 環境分離はIAMポリシーの正しさに依存する。アカウント境界による保護がない |
| CON-05 | Slackは Incoming Webhook のみ | 承認操作をSlackから行えない。通知は一方向 |
| CON-06 | GitHub Actionsのログは実行中に取得できない | ログのS3格納は別ワークフローになる（ADR-0009） |
| CON-07 | ALBはパスの書き換えができない | パス振り分け時、アプリ側が接頭辞を認識する必要がある（ADR-0013） |
| CON-08 | ドメインを保有していない | HTTPのみ。ホスト名振り分けができない |

### 実機検証の記録（2026-10-12 〜 10-14）

| ID | 検証方法 | 結果 |
|---|---|---|
| AC-04 | prodリリースを実行し、3段の承認を個別にクリック | `prod-approval-1/2/3` が段ごとに停止。監査記録に dev_lead / qa_po / sre が残る |
| AC-05 | DynamoDBのリリース履歴を確認 | 同一digestが build → stage → prod と記録。prodにタグ `appA/v1.0.0` |
| AC-06 | stageへデプロイしていないcommitでprodリリースを試行 | **事前チェックで停止**（承認を求める前） |
| AC-07 | stageのECSサービスの `desired_count` を手動変更 | 本物のドリフト1件を検知してIssue作成。誤検知2件は除外し、prodのIssueは作られなかった |
| AC-08 | 緊急リリース実行 → 通常prodリリースを試行 → 事後報告 → 再試行 | 未報告時は**停止**、報告後は**通過**。同じcommit・digest・チケットで結果が変わった |

**AC-06 と AC-08 はいずれも「承認を求める前」に停止している。**
承認者に通らないリリースを見せない設計（ADR-0003）どおりで、
3回の承認クリックを無駄にさせない。

### AC-03の達成記録（2026-10-11）

実機のCIで、埋め込みTomcatのCRITICAL 3件を検出してゲートが停止した。

```
## セキュリティゲート: 停止（モード: pr）
| CRITICAL | 3 |   | HIGH | 13 |   | MEDIUM | 5 |   | LOW | 1 |
実行したツール: gitleaks, semgrep, spotbugs, trivy

| CRITICAL | CVE-2026-65182 | 修正版 11.0.25, 10.1.58, 9.0.121 | trivy |
| CRITICAL | CVE-2026-65905 | 修正版 11.0.25, 10.1.58, 9.0.121 | trivy |
| CRITICAL | CVE-2026-68525 | 修正版 11.0.25, 10.1.58, 9.0.121 | trivy |
```

- **修正版が提供されているCRITICALのみ**が停止対象になっている（ADR-0008の基準どおり）
- HIGH 13件はPRモードでは停止させていない（stage/prodでは停止する）
- 対応は抑制ではなくTomcatのバージョン更新で行い、再実行で通過を確認した

**この検証の前は、同じCIが「検出0件」で成功していた。** `trivy fs` が
ロックファイルを前提とするため、Gradleアプリの依存が1件もスキャンされて
いなかった（設計書15章の7番）。
