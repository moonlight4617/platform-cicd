## 1. この文書の目的

設計・コードレビュー・ユニットテストをすべて通過したうえで、**実際に動かして
はじめて判明した問題**を記録する。

実務適用時に同じ失敗を繰り返さないための記録であり、
「設計段階でどこまで詰められるか」の限界を示す資料でもある。

## 2. 総括

### 2.1 実機検証なしに正しさを主張できなかった

**17件の問題が、実行してはじめて判明した。** すべて次をすべて通過した状態で発生した。

- `terraform validate`（3リポジトリ）
- YAML構文チェック（30ファイル）
- ユニットテスト（最終的に50項目以上）
- 設計書・ADRでの事前検討

| 分類 | 件数 |
|---|---|
| 権限（IAM / OIDC） | 6件 |
| ツール・ライブラリの実際の挙動 | 5件 |
| GitHub Actionsの仕様 | 3件 |
| 自分で作った制約が自分を止めた | 2件 |
| 制度設計の欠落 | 1件 |

### 2.2 最も危険だったのは「成功したまま誤った安心を与えるもの」

失敗して止まる問題は、気づけるので実害が小さい。
**危険なのは成功したまま間違っているもの**で、3件あった。

| # | 内容 | なぜ危険か |
|---|---|---|
| 1 | **Javaの依存ライブラリが1件もスキャンされていなかった** | CIは緑のまま「脆弱性0件」を報告し続けた。イメージスキャンを追加したら22件検出（CRITICAL 3 / HIGH 13） |
| 2 | **承認記録ジョブがデプロイ可能な権限を持っていた** | stageでは成功していたため気づけなかった。prodで3段に分けて初めて露出 |
| 3 | **ドリフト検知が毎回誤検知を出していた** | 件数が常に0で判断材料がなく、かつstage/prod両方で毎晩Issueが立つ状態。本物が埋もれる |

いずれも「動いている」ように見えていた。

### 2.3 NFR-05（fail closed）に穴があった

「検査・ビルドの失敗を問題なしとして通さない」を掲げ、
スキャンの失敗・SARIFの破損・レポート未生成をすべて停止条件にしていた。

しかし**「スキャン対象が存在しないこと」は検出できていなかった。**

```
検査が失敗した    → 検出できていた
検査対象がなかった → 検出できていなかった  ← 穴
```

「検出がないこと」と「検査していないこと」は区別しなければならない。
前者は安全を意味するが、後者は何も意味しない。

## 3. 権限（IAM / OIDC）— 最も多く、最も予見しにくかった

### 3.1 IAMのリソースパターンが実際のリソース名に一致しなかった

命名規約を `<service>-<app>-<env>[-suffix]` とし、IAMで `*-<env>-*` と絞っていた。
しかし**環境名で終わる名前には一致しない。**

| リソース | 実際の名前 | 旧パターン | 結果 |
|---|---|---|---|
| ロググループ | `/ecs/serviceA-appA-dev` | `/ecs/*-dev-*` | 不一致 |
| タスク定義 | `serviceA-appA-dev:3` | `task-definition/*-dev-*:*` | 不一致 |
| Lambda関数 | `serviceA-appB-dev` | `function:*-dev-*` | 不一致 |

3箇所すべてで `AccessDenied` になる状態だった。
**リソース名を実際に決めるまで検証できない**類の問題。

### 3.2 OIDCの sub が不変サブジェクト形式だった

ADR-0006で「`sub` をリポジトリ×環境の完全一致で列挙する」と決めたが、
GitHubは **`use_immutable_subject: true` が既定**で、subに
オーナーIDとリポジトリIDが含まれる。

```
想定: repo:moonlight4617/serviceA-appA:environment:ci
実際: repo:moonlight4617@70841616/serviceA-appA@1413353244:environment:ci
```

**名前ベースの信頼ポリシーは1つも一致しない。**

不変サブジェクトはリポジトリの改名・削除・再作成に対する耐性を持たせる仕組みで、
セキュリティ上望ましい。そのため回避せず、IDを明示する形に変更した。
未作成のリポジトリ（IDが分からないもの）にはAWSアクセスを許可しない設計にした。

**実務への示唆**: リポジトリを作り直すと信頼関係が切れる。
IDの管理をどこで行うか（Terraformの変数か、GitHub providerでの動的取得か）を
最初に決めるべき。

### 3.3 承認記録ジョブにデプロイ可能なロールを渡していた（最も重要）

ADR-0003で「段ごとに環境を分ける」と決めたが、
**それがIAMの信頼ポリシーとの整合を要求する**点を詰めていなかった。

承認ジョブは `prod-approval-1/2/3` 環境で動く。しかしprodロールの信頼ポリシーは
`environment:prod` しか許可していないため、承認記録ができず失敗した。

ここで安易に許可すると設計が壊れる。

| 案 | 問題 |
|---|---|
| prodロールを `prod-approval-*` に許可 | **1段目の段階でprodへデプロイでき、3段承認を迂回できる**（FR-25の破れ） |
| stageロールを使う | 承認記録のためにstageへのデプロイ権限を与えることになる |

**stageでは「たまたまstageロールで動いていた」ため成功しており、
気づけなかった。** 実は承認記録のためにstageへの完全なデプロイ権限を
持っていた状態だった。

対応として承認監査テーブルへの追記だけができるロールを作り、
デプロイに使える操作を明示的にDenyした。

**実務への示唆**: 「ジョブが何をするか」ではなく
「**どの環境の文脈で動くか**」でロールを設計する必要がある。
多段承認では承認の段数と同じだけ文脈が増える。

### 3.4 リソースレベル権限に対応していないAPIがあった

`ecs:DeregisterTaskDefinition` はARNを指定するとどのパターンでも
`implicitDeny` になる。`*` で許可し、環境の制限はタグ条件で行う必要があった。

IAMポリシーシミュレータ（`aws iam simulate-principal-policy`）で事前に検出できた。

### 3.5 タグ付けに別の権限が必要だった

`ecs:RegisterTaskDefinition` にタグを付けると、ECSは**別途
`ecs:TagResource` をタスク定義のARNに対して要求する。**

タグ付けは `aws:RequestTag/Environment` で環境を縛るための必須操作なので
省略できず、この権限がないとタスク定義を1つも作れない。

### 3.6 IAMポリシーシミュレータの使い方に注意が必要だった

有効な事前検証手段だったが、**条件キーを与えないと誤って拒否と判定される。**

```
iam:AttachRolePolicy （条件キーなし）                    implicitDeny  ← 誤検出
iam:AttachRolePolicy （iam:PolicyARN を指定）            allowed
iam:AttachRolePolicy （AdministratorAccess を指定）      implicitDeny  ← 正しい拒否
```

`iam:PolicyARN` や `iam:PassedToService` を条件に使っている場合は
`--context-entries` で値を渡す必要がある。

一方で、設計意図が効いていることの確認には有効だった。

```
s3:PutObject  dev用ロール → prodのtfstate     implicitDeny   ← 環境分離
iam:AttachRolePolicy  AdministratorAccess     implicitDeny   ← 権限昇格の防止
```

## 4. セキュリティ検査

### 4.1 Javaの依存ライブラリがスキャンされていなかった（最重要）

`trivy fs` はロックファイル（`gradle.lockfile` / `package-lock.json` /
`requirements.txt` など）を見て依存関係を解決する。

Gradleでロックファイルを使っていないと**依存ライブラリが1件もスキャンされない。**

| | 検出件数 |
|---|---|
| `trivy fs` のみ | **0件** |
| コンテナイメージのスキャンを追加 | **22件**（CRITICAL 3 / HIGH 13 / MEDIUM 5 / LOW 1） |

CIは成功したまま「脆弱性0件」を報告し続けていた。

対策として、CIでコンテナイメージをビルドし（pushはしない）
`trivy image` で実際に同梱される依存をスキャンする形に変えた。
加えて、Javaでロックファイルもイメージもない場合は明示的に失敗させた。

### 4.2 Gradleの依存バージョン上書きが効いていなかった

検出されたJacksonのHIGH 5件を直すため `dependencies { constraints { ... } }` で
バージョンを固定したが、**効いていなかった。**

`io.spring.dependency-management` プラグインのBOMによるバージョン管理が
Gradleのconstraintsより優先されるため、指定が無視される。

```
dependencies { constraints { ... } }        効かない
extra["jackson-bom.version"] = "3.1.7"      効く
```

**「修正したつもりで実際は直っていない」状態だった。**
CIが `pr` モードでCRITICALのみを停止条件にしていたため気づきにくく、
stageモードで検証して初めて分かった。

プロパティ名は `spring-boot-dependencies` のpomで確認する必要がある。

### 4.3 基盤自身の設計判断がゲートに引っかかった

stageモードのゲートが、基盤の `secrets: inherit` をHIGH 8件として検出した。
Semgrepの指摘は一般論として正しいが、これは意図した設計判断だった。

| 観点 | 内容 |
|---|---|
| 明示列挙にした場合 | 新しいシークレット追加時に**全アプリリポジトリの改修**が必要。一部だけ更新されていない状態が生まれ、チーム間のバラツキになる（G-01に反する） |
| 実際のリスク | ロールARNは識別子であり、OIDCの環境固定により値を持っていてもロールを引き受けられない。実際の資格情報はSlack Webhookのみで、全ワークフローが正当に必要とする |

ここで**ADR-0008の設計上の欠落が露出した。**

## 5. 制度設計の欠落

### 5.1 すべての抑制に期限を課す設計では恒久的な判断を表現できなかった

ADR-0008は抑制に有効期限（最長180日）を必須とし、期限切れを停止条件にしていた。
これは「後で直す技術的負債」を想定した設計である。

恒久的な設計判断を期限付きで表現すると、次のどちらかが起きる。

| 起きること | 結果 |
|---|---|
| 180日ごとに同じ例外を機械的に更新する | 期限が儀式化し、**本当に一時的な抑制の期限も重みを失う** |
| 更新を忘れて失効する | 無関係な変更のCIが赤くなり、慌てて再追加するか基準を緩める |

**期限切れを停止条件にしているからこそ、この区別が必要だった。**

対策として `permanent` という別枠を設け、期限ではなく見直し周期で管理した。
乱用を防ぐため `adr`（判断の根拠となる記録）を必須にし、
見直し期限の超過は停止させず警告を出し続ける形にした。

**ただし `adr` の必須化は「根拠を書かせる」ところまでしか強制できず、
根拠の妥当性は人間が判断する必要がある。** ここは仕組みで守れない。

## 6. 自分で作った制約が自分を止めた

### 6.1 IAM Denyが自分のS3アップロードを阻んだ

レポートのライフサイクル判定に `Kind` タグを使うため、
タグのない `PutObject` をIAMでDenyしていた。

しかし **`aws s3 cp` はアップロード時にタグを付けられない。**
「アップロードしてから後でタグを付ける」構成はアップロード自体が
Denyされるため成立しなかった。

1ファイルずつ `aws s3api put-object --tagging` で上げる形に変えた。

### 6.2 ECRのIMMUTABLEタグが成果物の再利用を阻んだ

「同じcommitから別のイメージができる」ことを防ぐためタグをIMMUTABLEにしていた。
その結果、mainでビルド済みのcommitをあとからdevへデプロイしようとすると
再pushで失敗した。

これはADR-0005の観点では**「同じcommitを作り直さない」のが正しい**ため、
既存の成果物のdigestを再利用する形に変えた。
結果として「ビルド済みならビルドをスキップする」という望ましい挙動になった。

### 6.3 変数のvalidationがCIのplanを壊した（設計から予見できた）

stage/prodで `image_digest` を必須にすると（ADR-0005をvalidationで強制）、
デプロイではないCIのplanが通らない。

DynamoDBから「その環境にデプロイされている成果物のdigest」を引いて渡す形にした。
固定のダミー値だとplanに毎回差分が出てレビュー価値が落ちる。

**この1件だけは実機検証の前に自分で気づいて対処した。**

## 7. ドリフト検知

### 7.1 ドリフトの件数が常に0だった

`terraform plan -refresh-only` のドリフトは `resource_changes` ではなく
**`resource_drift`** に入る。集計が前者だけを見ていたため、
Issueは「ドリフトを検知しました」と言いながら件数 0/0/0 を表示していた。

人間が対応を判断するための情報が何も載っていない状態だった。

### 7.2 読み取り専用の計算属性が毎回ドリフトとして現れた

stage / prod の両方で、毎回同じ2件が検出されていた。

| リソース | 属性 | 実体 |
|---|---|---|
| `aws_iam_role` | `managed_policy_arns` | `aws_iam_role_policy_attachment` を使う構成での既知の競合 |
| `aws_lb_target_group` | `load_balancer_arns` | プロバイダ側で読み取り専用 |

`-refresh-only -detailed-exitcode` は**refresh中にstateのどの属性が変わっても
終了コード2を返す**ため、これらも「ドリフトあり」として扱われていた。

**ADR-0012が「Issueが滞留し、対応されない状態が常態化する」として
懸念していた事態が、誤検知によって確実に起きる状態だった。**

### 7.3 「無視する」と「差分がない」の区別が必要だった

`config/drift-ignore.yaml` に載せるのは「実際に差分がないもの」だけとした。

「ノイズだから無視する」は本物のドリフトなので対応が必要である。
この区別を崩すとドリフト検知そのものが意味を失う。
そのため各エントリに理由の記述を求め、レビューで判断できる形にしている。

### 7.4 未デプロイ環境のドリフト検知は無意味だった

比較対象の実態が存在せず、plan上は「全部作成」になるだけ。
DynamoDBのデプロイ実績を確認し、実績がなければスキップするようにした。

## 8. GitHub Actionsの仕様

### 8.1 再利用可能ワークフローのpermissionsがジョブの上限になる

ワークフローレベルの `permissions: contents: read` がGITHUB_TOKENの上限になるため、
OIDCを使うジョブには **`id-token: write` をジョブレベルで明示する必要がある。**

ないと「Could not load credentials from any providers」で失敗する。
呼び出し側で `id-token: write` を付けても効かない。

### 8.2 同一環境を使う複数ジョブは1回の承認で通過する

stageは「承認」ジョブと「デプロイ」ジョブが両方 `stage` 環境なので、
1回の承認で両方が進む。

prodは `prod-approval-1/2/3` と環境を分けているため段ごとに個別の承認が必要。
**ADR-0003で「1つの環境に3人を登録すると誰か1人の承認で通ってしまう」として
環境を直列にした判断が、実機でも正しかった。**

### 8.3 composite action内の相対パス参照は呼び出し側を指す

composite action内で `uses: ./actions/xxx` と書くと、
**呼び出し側リポジトリ**を参照してしまう。完全なリポジトリパスで指定する必要がある。

## 11. 設計として正しかったこと

実機検証で裏付けが得られた判断も記録しておく。

| 判断 | 裏付け |
|---|---|
| **ADR-0002: publicのまま機密を隔離** | Free planのpublicリポジトリで承認者必須設定が使えることを確認。機密をリポジトリに置かない設計はprivateでも正しい |
| **ADR-0003: 承認段数を環境の直列で表現** | 同一環境は1回の承認で通過するため、段を分けるには環境を分ける必要があった |
| **ADR-0003: 検査を承認の前に実施** | AC-06・AC-08の停止がいずれも承認を求める前に起きた。承認者に通らないリリースを見せない |
| **ADR-0005: ECR pushをdevロールだけに付与** | stage/prodのパイプラインが新しいイメージを作れないことを権限として保証できた |
| **ADR-0005: digestで指定** | 同一digestの昇格が記録から追跡できた |
| **ADR-0011: 催促ではなくブロック** | 同じcommit・digest・チケットで、事後報告の有無だけが結果を変えた |
| **ADR-0012: 自動applyしない** | ドリフトの対応判断を人間に残す形が機能した |
| **基盤自身にテストを持たせる** | `check_yaml.py` が実際のYAML構文エラー（`承認: SRE` のコロン）を検出した |

## 12. 実務適用時に最初に決めるべきこと

この検証から導かれる、設計段階で詰めておくべき項目。

| # | 項目 | 理由 |
|---|---|---|
| 1 | **IAMの設計は「ジョブが何をするか」ではなく「どの環境の文脈で動くか」から始める** | 多段承認では承認の段数だけ文脈が増える。承認記録のような副次的な処理にも専用の権限が必要になる |
| 2 | **OIDCの不変サブジェクトを前提にする** | リポジトリIDの管理方法（変数か動的取得か）を最初に決める。リポジトリ再作成時の手順も |
| 3 | **依存スキャンの対象が存在することを検証する** | ロックファイルの有無やイメージスキャンの実施を、アプリ側の規約として強制する |
| 4 | **抑制に「一時的」と「恒久的」の2種類を用意する** | 片方しかないと、期限が儀式化するか基準が緩む |
| 5 | **ドリフト検知の誤検知を先に潰す** | 誤検知が出る状態で運用を始めると、Issueが無視される習慣がつく |
| 6 | **IAMポリシーシミュレータを設計時から使う** | 条件キーを渡す前提で、権限の検証をCIに組み込むことも検討できる |
| 7 | **「成功したまま間違っている」状態を探す観点を持つ** | 失敗して止まるものは気づける。検出0件・過剰権限・誤検知はいずれも緑のまま進む |
