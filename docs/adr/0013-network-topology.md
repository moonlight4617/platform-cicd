# ADR-0013: ALB 1台のパス振り分け + パブリックサブネット構成とする

- **状態:** 承認済み
- **日付:** 2026-09-30
- **関連:** ADR-0005, ADR-0006, ADR-0014

## 背景

実験は1つのAWSアカウントでdev/stage/prodの3環境を動かす（ADR-0006）。
ECSアプリはappAとappCの2つ、つまり合計6サービスが動く。

ここでコストが問題になる。

- ALBは1台あたり月20ドル強。環境ごとに立てると月60ドル超
- Fargateをプライベートサブネットに置くと、ECRからのイメージ取得のために
  NAT Gateway（月32ドル前後）またはVPCエンドポイントが必要

実験としてこのコストを負担する意味は薄い。

## 決定

### ALB: 1台をパス振り分けで共有する

```
ALB 1台（platform-infra が管理）
├─ /dev/appA/*    → serviceA-appA-dev   のターゲットグループ
├─ /stage/appA/*  → serviceA-appA-stage
├─ /prod/appA/*   → serviceA-appA-prod
├─ /dev/appC/*    → serviceA-appC-dev
├─ /stage/appC/*  → ...
└─ /prod/appC/*   → ...
```

- **ALBはパスの書き換えができない**ため、各アプリが自分のパス接頭辞を認識する必要がある。
- パス接頭辞は **実行時の環境変数として注入する**（ADR-0005の原則に沿う）。
  - appA（Spring Boot）: `SERVER_SERVLET_CONTEXT_PATH=/dev/appA`
  - appC（TypeScript）: フレームワークのbasePath相当の設定を環境変数から読む
- リスナールールの管理は `platform-infra` が行う。
  アプリ側はターゲットグループを作り、ルールの登録に必要な値をSSM経由で受け渡す（ADR-0014）。

### サブネット: パブリックサブネット + パブリックIP付与

- Fargateタスクをパブリックサブネットに配置し、`assign_public_ip = true` とする。
- NAT GatewayもVPCエンドポイントも作らない。
- **セキュリティグループで、インバウンドはALBのセキュリティグループからのみ許可する。**
- **本構成は本番想定ではない**ことをREADMEに明記する。

### VPC / ALBの所有

VPCとALBは3環境で共有するため、`serviceA-infra` ではなく **`platform-infra`** が所有する
（ADR-0001の構成どおり）。

## 理由

- **ALBを1台にするのがコスト削減として最も効く。** 月40ドル強の削減になり、
  実験の趣旨（CI/CDの検証）を損なわない。
- **パス振り分けを選んだのは、ドメインを保有していないため。** ホスト名振り分け
  （`appa-dev.example.com`）の方が実務に近く、アプリ側の改修も不要だが、
  ドメインとRoute53のホストゾーンが必要になる。
- **パス接頭辞を環境変数で渡す構成は、ADR-0005の「環境差は実行時に注入する」原則と一致する。**
  結果的に、この原則が実際に機能するかを検証する題材にもなる。
- **パブリックサブネットを選んだのは、NAT Gatewayが実験のコストとして最も重いため。**
  VPCエンドポイント（月7ドル程度）でも実務に近づけられるが、実験では不要と判断。
  セキュリティグループでALB経由のみに絞れば、外部から直接到達はできない。
- **VPC/ALBをplatform-infraに置いたのは、サービスが増えても1つのALBを共有できるから。**
  serviceA-infraに置くと、serviceBを追加したときにALBをもう1台立てることになる。

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| 環境ごとにALBを立てる | 実務に近い構成 | 月60ドル超。実験で負担する意味が薄い |
| ホスト名で振り分ける | `appa-dev.example.com` | ドメインとRoute53ホストゾーンが必要 |
| ECSを常時起動せず、検証時のみdesired_countを上げる | コストをさらに削減 | 起動状態の管理が実験のノイズになる。ALB共有で十分安い |
| プライベートサブネット + NAT Gateway | 最も実務に近い | 月32ドル。実験では過剰 |
| プライベートサブネット + VPCエンドポイント | 実務に近くNATより安い | 月7ドル程度。パブリックサブネットで足りる |
| ALBのパス書き換えを使う | アプリの改修を回避 | ALBにパス書き換え機能はない（リダイレクトのみ） |

## 結果とトレードオフ

**得たもの**

- 月40〜70ドル規模のコスト削減
- ADR-0005の原則（環境差は実行時注入）を実際に検証する題材が得られた

**諦めたもの・新たな負担**

- **アプリがパス接頭辞を意識する必要がある。** 本来アプリはデプロイ先のパス構造を
  知るべきではない。実務でホスト名振り分けに移行すれば不要になる負担であり、
  **実験のための不自然さがアプリのコードに入り込んでいる**点は認識しておく必要がある。
- **パブリックサブネット配置は本番構成として不適切。** セキュリティグループで守っては
  いるが、多層防御になっていない。実務移行時は必ずプライベートサブネットに変更する。
- **ALBが単一障害点であり、かつ3環境で共有されている。** ALBのリスナールールの変更ミスが
  全環境に影響する。prodのルールをdevの作業で壊す事故が起こりうる。
- `platform-infra` がアプリのターゲットグループを参照するため、
  platform-infraとアプリリポジトリの間に依存が生まれる（ADR-0014で緩和）。

## 見直しの契機

- ドメインが使えるようになったとき → ホスト名振り分けに変更し、
  アプリのパス接頭辞の設定を削除する
- 実務適用時 → プライベートサブネット + VPCエンドポイント（またはNAT）、
  環境ごとのALBまたはアカウント分離へ変更する
- ALBのルール変更で環境をまたぐ事故が起きたとき
