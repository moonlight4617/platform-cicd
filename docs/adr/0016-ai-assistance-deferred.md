# ADR-0016: AI支援機能の方式決定は保留する

- **状態:** 保留
- **日付:** 2026-09-30
- **関連:** ADR-0002, ADR-0008

## 背景

当初の要件に、必須ではないものとしてAIを使う機能が2つ挙げられていた。

1. **静的解析・脆弱性診断の結果に問題があった際に、修正案をAIに提案してもらう**
2. **コード差分からドキュメントの更新必要箇所を判断して更新するAIを組み込む**
   （ドキュメントリポジトリを分け、PRを作るところまで）

どちらもソースコードを外部のモデルに送ることになる。リポジトリをpublicにしたとはいえ
（ADR-0002）、実務適用時はinternalリポジトリの社内コードを扱うため、
データの取り扱いに関する判断が必要になる。

## 決定

**方式の決定を保留する。** 現段階では実装しない。

保留する理由と、後で判断するために必要な検討事項を以下に記録する。

### 後で判断すべき事項

**A. モデルの呼び出し経路**

| 経路 | 特徴 |
|---|---|
| Amazon Bedrock | AWSアカウント内で完結。VPCエンドポイント経由にできる。IAMで権限制御。クロスリージョン推論時のデータ経路を確認する必要がある |
| Anthropic API直接 | 設定が簡単。外部サービスへの送信になるため、社内のデータ取り扱い規定との照合が必要 |

実験がAWS前提であることから **Bedrockが有力**だが、次の点を確認する必要がある。

- 社内のデータ取り扱い規定で、ソースコードをどこまで送信できるか
- モデル呼び出しのログ（プロンプト・レスポンス）をどこに保存するか、
  保存する場合その内容が機密になる
- 送信するコードの範囲をどう絞るか（差分のみか、周辺コードを含めるか、
  リポジトリ全体をコンテキストに入れるか）

**B. 修正案提案の実装方式**

- 入力: SARIF（ADR-0008）と該当箇所のコード
- 出力: PRコメント。**コードを自動で変更させるかは別途判断**
- 提案が誤っていた場合の扱い（提案を信頼して適用した結果の責任分界）

**C. ドキュメント更新の実装方式**

- 別リポジトリへPRを作るには **GitHub AppのトークンまたはPAT** が必要
  （デフォルトの `GITHUB_TOKEN` は自リポジトリしか操作できない）
- publicリポジトリでPATを扱う場合の漏洩リスク → GitHub Appの方が望ましい
- トリガーはmainへのマージか、prodリリース完了後か
- 生成されたPRのレビュー体制（AIが作ったPRを誰がレビューするか）

## 理由

- **セキュリティ面のベストプラクティスを確認してから決めたいという判断があった。**
  一度実装して経路を作ってしまうと、後から「そのデータは送ってはいけなかった」と
  分かったときの影響が大きい。コードの送信は取り消せない。
- **AI支援は本基盤の目的（デプロイ精度のバラツキをなくす）に対して補助的な位置にある。**
  必須ではないと当初から位置づけられており、先に作る理由がない。
- **先に承認ゲート・スキャンゲート・ドリフト検知を動かす方が、判断に必要な材料が揃う。**
  実際にスキャン結果のSARIFがどういう内容になるか、ドキュメントの更新が本当に
  必要なのかが分かってから設計した方が、的を外さない。
- 保留のまま放置せず、検討事項をADRとして書き残すことで、
  後から判断を再開する際の起点になる。

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| 先にAnthropic APIで実装し、後でBedrockに差し替える | 動くものを早く作る | コードを送信する経路を規定の確認前に作ることになる。差し替え前に送ったデータは取り消せない |
| モックで実装し、呼び出しだけ後回し | インターフェースだけ先に作る | 実際の入出力が分からない状態でインターフェースを決めると、作り直しになる |
| AI支援を要件から外す | 実装しないと決める | 有用性は否定されていない。判断を先送りするのが実情に合う |

## 結果とトレードオフ

**得たもの**

- データ取り扱いの判断を、実装より前に行える
- 先行する機能の実装から、設計に必要な材料が得られる

**諦めたもの・新たな負担**

- **AI支援による効果（修正案の提示、ドキュメントの追従）が当面得られない。**
  特にドキュメントの陳腐化は、保留している間に進行する。
- **保留が長期化すると、そのまま忘れられる危険がある。** 見直しの契機を明記して対処するが、
  期限を設けていないため確実ではない。
- 後から組み込む際に、既存のワークフローへの後付けになる。
  最初から想定して作るより実装が不自然になる可能性がある。

## 見直しの契機

- **承認ゲート・スキャンゲート・ドリフト検知が動き、実際のSARIFの内容を確認できたとき**
  → 修正案提案の設計を開始する
- 社内のデータ取り扱い規定について、ソースコードの送信可否が確認できたとき
  → 呼び出し経路（Bedrock / Anthropic API）を決定する
- ドキュメントの陳腐化が実際に問題として現れたとき
  → ドキュメント更新の自動化を優先度を上げて検討する
