# ADR-0010: 承認・リリース・擬似チケットの記録はDynamoDBで管理する

- **状態:** 承認済み
- **日付:** 2026-09-30
- **関連:** ADR-0003, ADR-0004, ADR-0005, ADR-0011

## 背景

要件は次の3点。

- 各承認ゲートでの承認可否の状態を管理する
- 本番リリースと擬似チケットツールを紐づける（リリースのcommit ID / タグをチケットに記録）
- 擬似チケットツールはDynamoDBで表現する

一方でADR-0003により、**承認判定の正本はGitHub Environments**とした。
このためDynamoDBの役割を明確に定義する必要がある。

## 決定

### 役割の定義

**DynamoDBは「記録」と「参照」に限定する。承認の判定には使わない。**

| 用途 | 正本 | DynamoDBの役割 |
|---|---|---|
| 承認の可否判定 | GitHub Environments | 監査記録として複製を保持 |
| リリース履歴 | DynamoDB | 正本 |
| 擬似チケット | DynamoDB | 正本 |
| 昇格の可否（stage成功済みか） | DynamoDB | 正本（ADR-0004の検証に使用） |

### テーブル設計

3テーブル構成。PAY_PER_REQUEST、PITR有効。

**`releases`**

| 属性 | 例 | 用途 |
|---|---|---|
| `release_id` (PK) | `serviceA-appA#prod#20260930-001` | |
| `service` / `app` / `env` | | |
| `commit_sha` | `a1b2c3d...` | 成果物の識別（ADR-0005） |
| `image_digest` | `sha256:...` | 成果物の識別。`build_per_env` の場合は環境ごとのmap |
| `git_tag` | `appA/v1.4.0` | prodリリース時に付与 |
| `ticket_ids` | `[TICKET-123]` | |
| `approvals` | `[{gate, persona, github_user, approved_at}]` | 監査記録 |
| `scan_report_s3` | `s3://.../reports/` | ADR-0009へのリンク |
| `result` | `success` / `failed` / `rolled_back` | |
| `emergency` | `true` / `false` | ADR-0011 |
| `postmortem_filed` | `true` / `false` | ADR-0011 |
| `deployed_at` | | |

- GSI: `app-env-index`（`service#app` + `deployed_at`）。
  「このアプリの最新の成功リリース」「stage成功済みのdigest一覧」を引くため。

**`tickets`**

| 属性 | 用途 |
|---|---|
| `ticket_id` (PK) | `TICKET-123` |
| `title` / `status` / `assignee` | |
| `release_ids` | 紐づいたリリース |

**`approval_audit`**

承認イベントの追記専用テーブル。`release_id` + `gate` をキーに、
承認・却下・タイムアウトを時系列で残す。

### チケットの紐づけ方法

- **PRのタイトルまたはブランチ名から `TICKET-\d+` を自動抽出する。**
- **Releaseワークフローの手動実行時に、抽出結果を初期値として表示し、人間が確定させる。**
- prodリリース成功時に、Gitタグを作成し、`commit_sha` / `git_tag` / `image_digest` の
  3つすべてをチケットに記録する。

### 操作方法

実験段階では **AWS CLIを叩く簡易スクリプトのみ**を用意する（`scripts/ticket.sh` 等）。
画面は作らない。

## 理由

- **判定と記録を分けることで、正本が2つある状態を避けられる。** 承認をDynamoDBで判定すると、
  GitHubの承認履歴とDynamoDBの状態が食い違う余地が生まれる（ADR-0003の理由と同じ）。
  記録専用にすれば、食い違っても判定には影響しない。
- **昇格の可否判定をDynamoDBの正本にしたのは、GitHubに「この成果物はstageで成功したか」を
  問い合わせる手段がないため。** これはリリースの履歴から導出する情報であり、
  履歴の正本がDynamoDBである以上、ここに置くのが自然。
- **commit SHA・タグ・digestの3つすべてを記録するのは、それぞれ用途が違うため。**
  digestは同一性の保証（ADR-0005）、commit SHAはソースへの到達、
  タグは人間が読める識別子。どれか1つでは追跡が欠ける。
- **チケットIDを自動抽出しつつ人間に確定させるのは、自動抽出が外れるケースがあるため。**
  完全自動だと誤ったチケットに記録され、手入力のみだと入力漏れが起きる。
- **画面を作らないのは、実験の目的がCI/CDの検証であり、チケットツールの実装ではないため。**

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| DynamoDBを承認の正本にする | CLIで承認を書き込む | 正本が2つになる。ADR-0003で却下済み |
| 単一テーブル設計 | 1テーブルにすべて格納 | 実験段階では3テーブルの方が読みやすい。アクセスパターンも少ない |
| リリース履歴をGitタグのみで管理 | DynamoDBを使わない | 承認者の記録、スキャン結果へのリンク、緊急リリースの状態を持てない |
| チケットIDを完全自動抽出 | 人間の確定を省く | 抽出が外れたときに誤記録される |
| チケット管理画面を作る | Web UIを用意 | 実験の範囲外。CLIで足りる |

## 結果とトレードオフ

**得たもの**

- 承認判定の正本が1つに保たれる
- リリースの追跡に必要な情報（誰が承認し、何を出し、どのスキャン結果か）が1か所に揃う
- 昇格の可否をパイプラインから機械的に検証できる

**諦めたもの・新たな負担**

- **DynamoDBへの書き込みが、リリースの成否に影響する経路になる。** 昇格判定の正本である以上、
  書き込みが失敗するとその後のprodリリースが進めない。書き込み失敗時のリトライと、
  失敗が検知されなかった場合の復旧手順が必要（未決定）。
- **承認記録がGitHubとDynamoDBに二重に存在する。** 監査時にどちらを見るかの取り決めが必要。
  判定はGitHubが正だが、記録としてはDynamoDBを参照する運用になる。
- **CLIスクリプトのみなので、チケットの登録・更新に人間の手作業が残る。** 実務では
  既存のチケットツール（Jira等）との連携に置き換わる前提。
- テーブル設計が実験用のアクセスパターンに最適化されており、実務の要求で変わる可能性が高い。

## 見直しの契機

- 実務適用時、実在のチケットツールと連携するとき → `tickets` テーブルは廃止し、
  外部システムのIDを `releases` に持つ形に変わる
- DynamoDBの書き込み失敗でリリースが止まる事故が起きたとき
- リリース履歴の参照要求が増え、CLIでは足りなくなったとき

## 補足（2026-10-02 実装時に決定）

本ADRおよびADR-0004で未決定としていた「DynamoDBへの書き込みが失敗したときの扱い」を
決定した。

### 決定

**リリース記録の書き込み失敗は、デプロイの失敗として扱う。**

- 書き込みは3回までリトライする（指数バックオフ）。
- 3回失敗した場合、**ジョブを失敗させる**。
- Slackに「デプロイは完了したが記録に失敗した」旨を通知する（ADR-0015）。
- IAMポリシー上、デプロイロールには `dynamodb:DeleteItem` を与えていないため、
  記録を消して取り繕うことはできない。

### 理由

**記録のない成功を作らないため。** このテーブルは昇格判定（同じ成果物がstageで
成功済みか）の正本である。記録が欠けた状態を「成功」として通すと、
次のprodリリースで「stageを通っていない」と判定され、原因不明のまま止まる。
その時点では、なぜ記録がないのかを追う手がかりが残っていない。

失敗させておけば、記録が欠けていることがその場で分かる。

### 懸念点（意図した副作用として残すもの）

| 懸念 | 内容 |
|---|---|
| **AWSリソースの状態とジョブの結果が食い違う** | デプロイ自体は完了しているのに、ジョブは赤になる。実行者は「デプロイは失敗したのか、成功したのか」を自分で確認する必要がある。Slack通知とジョブのログで区別できるようにするが、**誤解を生みやすい状態であることは変わらない** |
| **再実行で解決しない場合がある** | 記録だけを後から書き込む手段を用意していない。DynamoDBの障害が続く間、リリースは再実行しても失敗し続ける |
| **手動での記録追加が必要になる可能性** | その場合、CLIスクリプト（`scripts/record-release.sh`、未作成）で記録を追加する運用になる。この経路は「デプロイせずに記録だけ作る」ことも可能にしてしまうため、昇格判定の抜け道になる |
| **DynamoDBが単一障害点になる** | DynamoDBが落ちている間、prodリリースができない。可用性は高いサービスだが、リリース経路がこのテーブルに依存していることは認識しておく必要がある |

3つ目の懸念（手動記録が抜け道になる）が最も重い。記録追加スクリプトを作る際は、
**実際にデプロイされたdigestをAWS側から確認してから書き込む**作りにして、
任意の記録を作れないようにする必要がある。
