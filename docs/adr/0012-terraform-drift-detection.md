# ADR-0012: ドリフト検知は定期実行し、対応判断は人間が行う

- **状態:** 承認済み
- **日付:** 2026-09-30
- **関連:** ADR-0004, ADR-0007

## 背景

要件は「CIでTerraformのドリフトを検知した際に、applyするかimportするか等の判断を
人間が行えるようにしたい」こと。

ドリフト（コードとAWSの実態の乖離）への対応は、状況によって正解が変わる。

- コードが正しく実態が誤っている → applyして戻す
- 実態が正しくコードが古い → コードを直す、またはimportする
- 意図した差分（手動対応の結果など） → 無視する

この判断は自動化できない。またADR-0007により、Terraformがリソースの唯一の所有者に
なっているため、ドリフト検知が意味を持つ前提が整っている。

## 決定

### 検知のタイミング

| タイミング | 内容 |
|---|---|
| PRのCI | 変更対象のstateに対して `terraform plan` を実行し、意図しない差分がないか確認 |
| 定期実行（1日1回・深夜） | 全アプリ × 全環境に対して `terraform plan -detailed-exitcode -refresh-only` |

- 対象は `serviceA-infra`（infraA）とアプリ側のtfの **両方**。
- **CIおよび定期実行の中では絶対にapplyしない。**

### 検知時の動作

```
plan -detailed-exitcode の終了コードが 2（差分あり）の場合:
  1. plan結果をS3へ保存（ADR-0009）
  2. GitHub Issueを自動作成
       タイトル: [drift] serviceA-appA / prod
       本文: 差分の要約（リソース種別と件数のみ。詳細はS3リンク）
       ラベル: drift
  3. Slackへ通知（ADR-0015）
  4. 同一アプリ×環境のIssueが既に開いている場合は、新規作成せずコメントを追加する
```

### 対応の3択（人間が判断）

| 判断 | 操作 |
|---|---|
| **コードの状態に戻す** | 通常のReleaseワークフローを実行し、承認ゲートを通してapplyする |
| **実態を正とする** | コードを修正するPRを作る。既存リソースの取り込みが必要な場合は `import` ブロックを追加したPRを作る |
| **意図した差分として無視** | Issueに理由を記載して閉じる |

- **importは必ずPR経由とする。** `terraform import` コマンドを直接実行するのではなく、
  `import` ブロック（Terraform 1.5以降）をコードに追加してレビューを通す。

## 理由

- **CIの中でapplyしないのは、ドリフトの正しい対応が状況依存だから。** 自動applyすると
  「実態が正しかったケース」で正しい状態を破壊する。特にprodでの自動applyは
  障害対応の手動変更を巻き戻す危険がある。
- **定期実行を1日1回にしたのは、ドリフトの発生から検知までの遅れと、実行コストの
  釣り合いから。** ドリフトは手動変更やコンソール操作で発生するため、営業時間内に起きて
  翌朝に検知されれば十分。1時間ごとに回す価値は薄い。深夜にしたのは、
  日中の変更作業中の中間状態を差分として拾わないため。
- **GitHub Issueを起点にしたのは、対応の記録が残り、担当を割り当てられるから。**
  Slack通知のみでは流れて消える。またIssueなら「無視すると判断した理由」を
  クローズ時のコメントとして残せる。
- **importをPR経由に限定したのは、`terraform import` の直接実行が記録に残らないから。**
  誰がいつ何を取り込んだかがstateの履歴にしか残らず、レビューも通らない。
  `import` ブロックならコードとして残り、レビューできる。
- **`-refresh-only` を定期実行で使うのは、コードの変更ではなく実態の乖離だけを見たいため。**

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| ドリフト検知時に自動apply | コードを常に正とする | 実態が正しいケースで正しい状態を破壊する。prodでは特に危険 |
| Slack通知のみ | Issueを作らない | 流れて消える。対応の記録と担当割り当てができない |
| 1時間ごとに検知 | 検知を早める | 日中の変更作業の中間状態を拾う。実行コストに見合わない |
| `terraform import` を直接実行するワークフロー | 手動実行でimport | 記録が残らず、レビューも通らない |
| dev環境のみ自動apply | 影響が小さい環境は自動化 | 環境ごとに挙動が違うと、devでの検証がstage/prodの予測にならない |

## 結果とトレードオフ

**得たもの**

- ドリフトの対応判断が人間に残り、正しい状態を破壊しない
- 対応の記録がIssueとして残る
- importがコードとしてレビュー可能な形で行われる

**諦めたもの・新たな負担**

- **ドリフトが自動では解消されない。** Issueが積まれるだけで対応されない状態になりうる。
  Issueの棚卸しという運用作業が新たに発生する。
- **検知が1日1回なので、ドリフト発生から最大約24時間の遅れがある。** その間に
  ドリフトを前提とした変更が加わると、対応が複雑化する。
- **全アプリ × 全環境のplanを毎晩実行するため、アプリ数に比例して実行時間が伸びる。**
  現状（4リポジトリ × 3環境 = 12回）は問題ないが、数十アプリになると実行時間と
  planの並列度を見直す必要がある。
- planの実行にはstateの読み取りとAWSの読み取り権限が必要なため、
  定期実行用のロールが常時有効な状態で存在する。

## 補足（2026-10-10 devを対象外にする）

**devはドリフト検知の対象外とする。**

ADR-0004の補足で、devを「開発者が自由にデプロイして動作確認するサンドボックス」と
定義した。devの状態は常に誰かの作業中コードであり、**「正しい状態」が定義されない。**
比較対象が存在しないため、ドリフト検知が原理的に意味を持たない。

当初は「実際にデプロイされているcommitと比較する」案も検討したが、devに対しては
比較しても得られる情報がない（差分があるのが正常な状態）。実装を増やす価値がない。

対象は `serviceA-infra` と各アプリの **stage / prod** のみとする。

これにより定期実行の対象が3分の2に減り、所要時間とコストも下がる。

## 補足2（2026-10-14 実機検証で判明した2つの問題）

ドリフトを人為的に作って検証したところ、**この実装では恒久的に誤検知を出し続ける**
ことが判明した。本ADRが「Issueが滞留し、対応されない状態が常態化する」として
懸念していた事態が、誤検知によって確実に起きる状態だった。

### 問題1: ドリフトの件数が常に0だった

`terraform plan -refresh-only` のドリフトは `resource_changes` ではなく
**`resource_drift`** に入る。集計が `resource_changes` だけを見ていたため、
Issueは「ドリフトを検知しました」と言いながら件数が 0/0/0 と表示されていた。

人間が対応を判断するための情報が何も載っていない状態だった。

### 問題2: 読み取り専用の計算属性が毎回ドリフトとして現れる

実機では stage / prod の両方で、毎回同じ2件が検出されていた。

| リソース | 属性 | 実体 |
|---|---|---|
| `aws_iam_role` | `managed_policy_arns` | `aws_iam_role_policy_attachment` を使う構成での既知の競合。ロール側の属性はTerraformの管理対象外だが、refreshで実態の値が入る |
| `aws_lb_target_group` | `load_balancer_arns` | プロバイダ側で読み取り専用。ECSサービスがアタッチした時点で値が入る |

`-refresh-only -detailed-exitcode` は **refresh中にstateのどの属性が変わっても
終了コード2を返す**ため、これらも「ドリフトあり」として扱われていた。

### 対策

1. **`resource_drift` を集計する。** リソース種別と**乖離している属性名**を報告する。
   属性値は報告しない（ARNやバケット名が入るため。ADR-0002）。
2. **`config/drift-ignore.yaml` で無視する属性を定義する。**
   platform-cicdが所有し、アプリ側では変更できない。
   無視する属性にはすべて理由を書く。
3. **アプリ側でも元から抑える。** `managed_policy_arns` は
   `lifecycle { ignore_changes = [...] }` で抑止できるため、規約として明記する。
4. **誤検知だけの場合はIssueを作らない。** 除外後のドリフトが0件なら通知しない。

### 「無視する」と「差分がない」の区別

`drift-ignore.yaml` に載せるのは「**実際に差分がないもの**」だけとした。

「ノイズだから無視する」は本物のドリフトなので対応が必要である。
この区別を崩すと、ドリフト検知そのものが意味を失う。
そのため各エントリに理由の記述を求め、レビューで判断できる形にしている。

### テストで固定した挙動

| 内容 |
|---|
| `resource_changes` が空でも `resource_drift` からドリフトを検知する |
| 誤検知を除外し、本物だけを「対応が必要」として報告する |
| **誤検知だけならIssueを作らない** |
| 要約に属性名は載せるが、**属性値は載せない** |

## 見直しの契機

- アプリ数が増え、定期実行の所要時間が許容範囲を超えたとき
- ドリフトのIssueが滞留し、対応されない状態が常態化したとき
  → 対応期限とエスカレーションの仕組みを追加する
- ドリフトの大半が特定の原因（例: オートスケーリングによるdesired_countの変化）に
  偏っていると判明したとき → その属性を `ignore_changes` で除外する
