# ADR-0015: Slack通知はIncoming Webhookのみとする

- **状態:** 承認済み
- **日付:** 2026-09-30
- **関連:** ADR-0003, ADR-0011, ADR-0012

## 背景

要件は「各承認者へは承認タイミングでSlack通知したい」こと。
加えてドリフト検知（ADR-0012）、緊急リリース（ADR-0011）でも通知が必要になる。

Slack連携の方式は2つある。

- **Incoming Webhook**: 通知の送信のみ。設定が簡単で権限申請も軽い
- **Slack App**: 双方向。インタラクティブなボタンによる承認操作が可能だが、
  App作成・権限設定・イベント受信用のエンドポイント（API Gateway + Lambda）が必要

## 決定

**Incoming Webhookのみを使う。通知は一方向とし、承認操作はSlackから行わない。**

- Webhook URLは **1つ（1チャンネル）**。環境やペルソナごとには分けない。
  URLはGitHub Secretsに格納する（ADR-0002）。
- **GitHubアカウントとSlackユーザーIDの対応表は
  `platform-cicd/config/approvers.yaml` で管理する**（ADR-0003と同一ファイル）。
- 通知処理はcomposite actionに集約し、アプリ側からは通知の内容だけを渡す。

### 通知する場面と内容

| 場面 | 内容 |
|---|---|
| 承認待ち | `<@Uxxxx>` メンション、対象アプリ・環境・ゲート段数、commit SHA、チケットID、**承認画面のURL** |
| デプロイ成功 | 対象アプリ・環境、commit SHA、git tag、実行者 |
| デプロイ失敗 | 対象アプリ・環境、失敗したジョブ、実行ログへのリンク |
| 脆弱性によるCD停止 | 対象アプリ・環境、検出件数、S3レポートへのリンク（ADR-0008） |
| ドリフト検知 | 対象アプリ・環境、差分の件数、GitHub IssueのURL（ADR-0012） |
| 緊急リリース実行 | 実行者、理由、インシデントID、対象digest（ADR-0011） |
| 事後報告の催促 | 未報告の緊急リリース一覧（ADR-0011） |

- **通知本文にARN・アカウントID・リソース名を含めない。** リンクで参照させる。
  Slackチャンネルは第三者に転送されうるため、ADR-0002の隔離方針を通知にも適用する。

## 理由

- **Slack Appによる承認操作を採用しなかったのは、承認判定の正本をGitHubに置いたため
  （ADR-0003）。** Slackから承認できるようにすると、判定経路が2つになる。
  Slackで承認した状態をGitHubのEnvironmentsに反映する仕組みが必要になり、
  「正本を1つにする」というADR-0003の判断と整合しなくなる。
- **通知の役割を「承認画面への誘導」に限定すれば、Webhookで十分。** 承認者が必要なのは
  「今承認が必要だと気づくこと」と「承認画面にすぐ飛べること」であり、
  Slack内で操作を完結させることは必須ではない。
- **チャンネルを1つにしたのは、実験段階では通知量が少なく分ける必要がないため。**
  また、通知の宛先が複数あると設定ミスで通知が届かない事故が起きやすい。
- **Slack Appを避けた実務的な理由として、ワークスペース管理者の権限申請とエンドポイントの
  運用（API Gateway + Lambdaの保守、署名検証）が発生する点がある。** 実験の主題ではない。
- **通知本文に機密を含めないのは、Slackが転送・スクリーンショット・外部共有されやすいため。**
  リポジトリをpublicにした判断（ADR-0002）と同じ発想で、機密の到達範囲を絞る。

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| Slack Appでボタン承認 | Slack内で承認を完結 | 判定経路が2つになる（ADR-0003と不整合）。App作成・権限申請・エンドポイント運用が必要 |
| 環境ごとにチャンネルを分ける | prod専用チャンネルなど | 実験段階では通知量が少ない。設定先が増えると通知漏れの事故が起きやすい |
| メール通知（GitHubの標準通知） | Environmentsの標準通知に任せる | 見落とされやすい。ドリフトや緊急リリースの通知は別途必要になる |
| 通知しない | 承認者が自分で見に行く | 承認待ちに気づかず、リリースが止まる |

## 結果とトレードオフ

**得たもの**

- 設定と保守がほぼゼロ（Webhook URL 1つ）
- 承認判定の正本が1つに保たれる
- 通知経路から機密が漏れない

**諦めたもの・新たな負担**

- **承認者はSlackからGitHubへ遷移する必要がある。** ワンクリックでは完了しないため、
  承認のリードタイムはSlack App方式より長くなる。
- **通知の到達を確認できない。** Webhookは送信のみなので、既読や反応を取れない。
  承認待ちが放置されているかどうかは、GitHub側を見ないと分からない。
  リマインドの再送はワークフロー側で実装する必要がある（未実装）。
- **チャンネルが1つなので、通知量が増えると重要な通知が埋もれる。** 特にprodの承認待ちが
  devのデプロイ通知に流される危険がある。アプリ数が増えたら分割が必要。
- Slack IDの対応表を手作業で維持する必要がある。異動や退職で古くなり、
  存在しないIDへのメンションは通知として機能しない（エラーにもならない）。

## 見直しの契機

- 通知量が増えて重要な通知が埋もれるようになったとき → チャンネルを分割する
- 承認のリードタイムが問題になったとき → Slack Appによるボタン承認を再検討する
  （その際はADR-0003の正本の扱いから見直す必要がある）
- 承認待ちの放置が実際に発生したとき → リマインドの再送を実装する
