# ADR-0011: 緊急リリース経路を設け、事後報告を強制する

- **状態:** 承認済み
- **日付:** 2026-09-30
- **関連:** ADR-0003, ADR-0004, ADR-0008, ADR-0010

## 背景

prodには3段階の承認ゲートを設ける（ADR-0003）。しかし本番障害の発生時、
3段階の承認を待っている間に被害が拡大する。

また、ADR-0008により「新たに公表された脆弱性によってprodリリースが突然止まる」ことが
起こりうる。障害対応中にこれに当たると復旧できない。

一方で、緊急経路を設けると「急いでいる」という理由で常用され、承認ゲートが
実質的に無効化される危険がある。

## 決定

**緊急リリース経路を設け、承認を1段（SRE）に減らす。ただし事後報告を仕組みで強制する。**

### フロー

```
1. emergency-release.yml を手動実行
   入力（すべて必須）:
     - 対象commit SHA または digest
     - インシデントID
     - 緊急リリースを行う理由（自由記述）
2. prod-emergency 環境で承認（承認者: sre 1名）
3. デプロイ実行
   - 脆弱性スキャンのゲートはスキップする（結果の記録は行う）
4. DynamoDBへ記録（ADR-0010）
     emergency: true
     postmortem_filed: false
5. Slackへ通知（実行者・理由・インシデントID・対象digest）
```

### 事後報告の強制方法

**未報告の緊急リリースが残っている間、同一アプリの通常prodリリースをブロックする。**

- Releaseワークフローの事前チェックで、`releases` テーブルを検索する。
- 対象アプリに `emergency: true` かつ `postmortem_filed: false` のレコードがあれば、
  **CDを失敗させる。**
- 事後報告はCLIスクリプトで登録する（`scripts/postmortem.sh`）。
  報告内容（原因・恒久対応・再発防止）を必須項目とし、`postmortem_filed: true` に更新する。
- 加えて、未報告のレコードがある場合は毎日Slackに催促を通知する（定期実行、ADR-0012と同じ枠）。

### 例外

- 事後報告が未完了でも、**緊急リリース経路は再度使える。** 障害が連続した場合に
  復旧手段を封じないため。ブロックされるのは通常リリースのみ。

## 理由

- **承認1段にSREを選んだのは、緊急時に必要な判断が「今出して安全か」という運用観点だから。**
  緊急時に開発リードやQAの承認を求めると、コードの妥当性の議論で時間を失う。
- **スキャンゲートをスキップするのは、脆弱性の停止と障害の復旧では障害の方が緊急度が高いため。**
  ただし結果の記録は行い、後から何を許容したかを追えるようにする。
- **催促通知ではなくブロックを選んだのは、通知は無視できるから。** 緊急リリースの事後報告は
  「重要だが急ぎではない」タスクなので、催促だけでは確実に後回しになる。
  次の通常リリースが止まれば、報告せざるを得ない状況が作られる。
- **ブロック対象を通常リリースに限定したのは、障害が連鎖したときに復旧を妨げないため。**
  緊急経路まで封じると、1回目の障害の事後報告が終わるまで2回目の障害に対応できない。
- **入力に理由とインシデントIDを必須としたのは、事後報告の起点になる情報だから。**
  後から「なぜこの緊急リリースをしたのか」が分からなくなると、事後報告そのものが書けない。

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| 緊急経路を作らない | 常に3段承認 | 障害時に復旧できない。運用として成立しない |
| 承認なしの緊急経路 | 0段 | 誤操作でのprodデプロイを防げない。1段は最低限必要 |
| 催促通知のみ（ブロックなし） | Slackで毎日リマインド | 無視できるため事後報告が滞る |
| 緊急経路も含めてブロック | すべてのリリースを止める | 障害の連鎖時に復旧手段がなくなる |
| 緊急リリースの回数上限を設ける | 月N回まで | 上限に達した時点で復旧できなくなる。同じ問題 |
| スキャンゲートも適用する | 緊急時も止める | 脆弱性のために障害復旧ができない状態になる |

## 結果とトレードオフ

**得たもの**

- 障害時に復旧できる経路が確保される
- 緊急経路の常用が構造的に抑止される（次の通常リリースが止まるため）
- 何を許容して出したかが記録に残る

**諦めたもの・新たな負担**

- **事後報告が未完了のアプリは、無関係な変更もprodに出せなくなる。** 抑止力の代償であり
  意図した挙動だが、報告を書く人が不在（休暇など）の場合にリリースが止まる。
  緊急時の抜け道として「SRE権限でフラグを手動更新する」経路が事実上必要になるが、
  これを正式に認めると抑止力が失われる。取り扱いは未決定。
- **緊急リリース時にスキャンゲートを迂回するため、既知の脆弱性を含む成果物がprodに出る。**
  記録は残るが、その後に是正する運用（いつまでに直すか）は定義していない。
- CLIスクリプトでの事後報告なので、報告内容の質は担保できない。
  必須項目を埋めるだけの形式的な報告になる余地がある。
- 緊急経路のワークフローが通常経路と別に存在するため、両方を保守する必要がある。

## 見直しの契機

- 事後報告未完了によるリリース停止が実際に業務を妨げたとき
  → SREによるフラグ更新を正式な例外として定義するか、猶予期間を設けるか検討
- 緊急リリースの頻度が高止まりしたとき → 通常リリースのリードタイムそのものを見直す
- 迂回した脆弱性の是正期限を定める必要が出たとき
