# ADR-0006: AWS認証はOIDC、環境分離は1アカウント内で行う

- **状態:** 承認済み
- **日付:** 2026-09-30
- **関連:** ADR-0002, ADR-0007, ADR-0013

## 背景

GitHub ActionsからAWSへアクセスする必要がある。実務ではdev/stage/prodをAWSアカウント単位で
分離する想定だが、実験では1アカウントで実施する。

また、リポジトリがpublicである（ADR-0002）ため、認証情報の扱いには通常以上の注意が必要。

## 決定

### 認証

- **OIDCによるIAMロールの引き受けのみを使う。** アクセスキーは発行しない。
- IAMロールは環境ごとに分ける（`gha-deploy-dev` / `-stage` / `-prod`）。
- **信頼ポリシーの `sub` 条件はリポジトリと環境まで厳密に指定する。** ワイルドカードで
  リポジトリを広く許可することは禁止する。

  ```json
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:moonlight4617/serviceA-appA:environment:prod"
    }
  }
  ```

- ロールARNはGitHub Secretsに格納する（ADR-0002）。

### 1アカウント内での環境分離

- **リソース名を `<service>-<app>-<env>-*` の規約で統一する**（例: `serviceA-appA-prod-svc`）。
- **すべてのリソースに `Environment` タグを付与する。**
- **IAMポリシーで、名前の接頭辞とタグによる操作制限をかける。** prod用ロールはdev/stageの
  リソースを操作できない状態にする。
- Terraform stateのキーを環境ごとに分ける（ADR-0007）。

## 理由

- **OIDCなら長期の認証情報が存在しないため、漏洩する対象がそもそもない。** publicリポジトリで
  実験する以上、アクセスキーを使う選択肢はない。
- **`sub` 条件を厳密にする理由はpublicリポジトリ特有のリスクにある。** 条件が
  `repo:moonlight4617/*` のように緩いと、同一アカウント配下に作られた別のリポジトリから
  prodロールを引き受けられてしまう。環境まで含めて固定することで、
  「prod環境のジョブでのみprodロールが使える」状態になり、承認ゲート（ADR-0003）を
  迂回したprodアクセスも防げる。
- **1アカウントでも名前規約とタグによる制限を入れるのは、実務のアカウント分離に移行したとき
  設計を変えずに済むようにするため。** 制限がない状態で作ると、後からアカウントを分ける際に
  「どのリソースがどの環境のものか」の判別から始めることになる。

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| IAMユーザーのアクセスキー | Secretsに保存 | 長期認証情報が存在する。publicリポジトリでは選択肢にならない |
| 1つのIAMロールを全環境で共用 | ロールを1つに | prodとdevの権限が同一になり、事故の影響範囲が環境を越える |
| `sub` をリポジトリ単位まで | `repo:.../serviceA-appA:*` | 承認ゲートを通らないジョブからもprodを操作できてしまう |
| 実験でも3アカウント | Organizations | 実験のセットアップコストが大きい。設計側で分離に対応していれば後から移行できる |

## 結果とトレードオフ

**得たもの**

- 長期認証情報がゼロ
- 承認ゲートとAWS権限が連動する（prod環境のジョブでなければprodを触れない）
- 実務のアカウント分離へ移行しやすい

**諦めたもの・新たな負担**

- **アカウント境界による分離がないため、分離の強度はIAMポリシーの正しさに依存する。**
  ポリシーの書き漏れが、そのまま環境をまたぐ操作の許可になる。アカウント分離なら
  設定ミスでも境界を越えられないが、その安全性は得られていない。
- **リソース名の規約とタグ付けが全アプリで守られることが前提になる。** Terraformモジュール側で
  命名を強制する仕組みが必要（アプリ側の自由記述に任せると崩れる）。
- 環境ごとにロールと信頼ポリシーを作るため、リポジトリ追加時の設定項目が増える。
- **1アカウントなので、コストが環境別に集計されない。** タグでの按分になる。

## 見直しの契機

- 実務適用に向けてAWSアカウントを分離するとき → 名前規約とタグは維持しつつ、
  IAMポリシーの接頭辞制限は不要になる
- IAMポリシーの穴により環境をまたぐ操作が発生したとき

## 補足（2026-10-02 実装時に具体化）

決定の内容は変えていないが、実装時に以下を確定させた。

**ロールは5種類とする。**

| ロール | sub 条件 | 用途 |
|---|---|---|
| `gha-ci` | 各リポジトリの `environment:ci` | PRでのplanと静的解析。読み取り専用 |
| `gha-deploy-dev` | 各リポジトリの `environment:dev` | dev環境のデプロイ |
| `gha-deploy-stage` | 各リポジトリの `environment:stage` | stage環境のデプロイ |
| `gha-deploy-prod` | 各リポジトリの `environment:prod`, `environment:prod-emergency` | prod環境のデプロイ |
| `gha-platform` | `platform-infra` の `environment:prod` のみ | 共有リソースとIAMの変更 |

**CIのplanも `environment: ci` を経由させる。** 当初は `pull_request` を sub 条件に
使う想定だったが、これだとPRという文脈でしか制限できず、「環境まで固定する」という
本ADRの原則から外れる。`environment: ci` を必ず通すことで、**すべてのAWSアクセス経路が
環境で固定された sub で表現される**状態になる。

**ADR-0005をIAMで強制する。** `gha-deploy-dev` だけが `ecr:PutImage` と
artifactsバケットへの `s3:PutObject` を持つ。stage/prodのロールは読み取りのみなので、
**環境別ビルドが権限として不可能**になる。ADR-0005は規約として書いたが、
この構成では仕組みとして守られる。

**platform-infra自身のapplyは `environment:prod` のみに限定する。** 共有リソース
（VPC・ALB）とIAMロール自体を変更するため、prodの3段承認を通したジョブでしか
実行できない状態にする。

**OIDCプロバイダは既存のものを参照する。** 実験対象のアカウントには既に
GitHubのOIDCプロバイダが存在していた（2024-06-13作成、`client_id_list` は
`sts.amazonaws.com` で適合）。OIDCプロバイダはアカウントに1つしか作れないため、
Terraformの管理下に取り込まず参照のみとする。取り込むと、このリポジトリの
`destroy` が他用途のOIDC連携を壊す。`create_oidc_provider = true` で
作成する経路も残している。

### 残したリスク: CIロールに `ReadOnlyAccess` を使っている

CIロール（`gha-ci`）には、個別のアクションを列挙する代わりにAWS管理ポリシーの
`ReadOnlyAccess` を付けている。**このため、PRのCIから全環境のtfstateファイルを
S3経由で読める。prod環境のstateも含まれる。**

| | |
|---|---|
| **採用理由** | 読み取りアクションを列挙する方式では、`terraform plan` が権限不足で落ちるリスクが高い。1つ漏れるたびにplanが失敗し、その原因がIAMだと分かりにくい。実験段階では安定性を優先した |
| **現状のリスク** | stateには平文の属性値が入る。RDSのパスワードをstateに持つ構成であれば、PRのCIから読める状態になる |
| **緩和されている点** | `secretsmanager:GetSecretValue` と `kms:Decrypt` は明示的にDenyしている。SecureStringの復号もできない。stateの書き込みはできない |
| **緩和されていない点** | state自体の読み取りは防げていない。PRを作れる人（= このリポジトリの書き込み権限を持つ人）は、ワークフローを書き換えてstateを外部に送り出せる |
| **実務での対応** | 実務では読み取りアクションを列挙して絞るべき。またstateに機密を置かない設計（秘密情報はSecrets Managerで参照のみ）を併せて守る必要がある |

実験では承認者が1アカウント（= PRを作れる人も1人）なので、現実的な攻撃面は小さい。
**ただし「CIは読み取り専用だから安全」という理解は誤り**であることを記録しておく。
