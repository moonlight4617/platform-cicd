# ADR-0004: CIとCDを分離し、trunk-based + 手動リリースとする

- **状態:** 承認済み
- **日付:** 2026-09-30
- **関連:** ADR-0003, ADR-0005, ADR-0012

## 背景

CIでは静的解析・脆弱性診断・Terraformのドリフト検知を行う。CDでは多段の承認ゲートを通す。
これらを同一のパイプラインで動かすか分けるかを決める必要がある。

特にドリフト検知は「applyするかimportするかを人間が判断する」という要件があり、
自動で流し切れない性質を持つ。

## 決定

**CIとCDを別のワークフローに分離する。** ブランチ戦略はtrunk-based（mainのみ）。

```
[PR作成・更新]  CI
                lint / テスト / 静的解析 / 脆弱性診断 / build / terraform plan
                → レポートをS3へ（ADR-0009）→ PRに要約コメント

[mainへマージ]  Build Artifact
                イメージを1回だけbuild → ECRへpush（タグ = commit SHA）
                → digestを記録（**デプロイはしない**。補足を参照）

[手動実行]      Deploy dev
                任意のブランチをサンドボックスへデプロイ（承認なし）

[手動実行]      Release
                入力: 対象commit SHA or タグ、環境、チケットID
                → stage（承認1段）→ prod（承認3段）→ 記録（ADR-0010）

[手動実行]      Emergency Release（ADR-0011）

[定期実行]      Drift Detection（1日1回・深夜、ADR-0012）
```

- **prodへのデプロイ前に「同じ成果物がstageで成功しているか」をDynamoDBで検証する。**
  未検証の成果物はprodに進めない。
- stageとprodは別々の手動実行とする（1つの実行で直列につながない）。
- ドリフト検知はCIの中では **applyしない**。検知のみを行い、対応は人間が判断する。

## 理由

- **stageで確認してからprodに出すまでの時間が、実運用では数時間〜数日空く。** 1つの実行で
  直列につなぐと、その間ワークフローが承認待ちで居座る。実行が長時間残ると、
  キャンセルや再実行の判断が複雑になる。
- **リリースは「コードが変わったこと」ではなく「出す判断をしたこと」を契機に起きる。**
  PRのマージとリリースは別の意思決定なので、トリガーも分けるのが素直。
- **ドリフト検知の結果に応じた分岐（apply / import / 無視）は人間の判断が必要で、
  パイプラインの中では表現できない。** CIは検知と通知までを責務とする。
- trunk-basedにすることで、環境とブランチの対応を管理する必要がなくなる。デプロイ対象は
  常に「どのcommit SHAか」だけで決まり、環境ごとにブランチが進んだり遅れたりする状態が
  発生しない。これはデプロイ精度のバラツキを生む代表的な原因。

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| CI/CD一体のパイプライン | PRマージから本番まで1本 | 承認待ちで実行が長時間残る。ドリフトの判断分岐が表現できない |
| GitFlow（develop/release/main） | ブランチで環境を表現 | 環境間のブランチ差分を管理する負担が発生。デプロイ対象がブランチ状態に依存し、精度のバラツキの原因になる |
| タグpushでCDを起動 | `v1.2.3` のpushでprodへ | タグ作成が実質のリリース操作になり、チケットIDなどの入力を受け取れない。誤pushの影響が大きい |
| stage→prodを1実行で直列 | 承認待ちでつなぐ | 上記の「実行が居座る」問題 |

## 結果とトレードオフ

**得たもの**

- 実行の寿命が短く、状態が追いやすい
- リリースの意思決定が明示的な操作として記録に残る
- ドリフト対応を人間の判断として扱える

**諦めたもの・新たな負担**

- **完全な自動リリースではない。** prodリリースは必ず人間の手動実行が必要。これは承認ゲート
  要件から必然だが、デプロイ頻度は上げられない。
- **「stageで成功した成果物か」の検証をDynamoDBに依存する。** DynamoDBの記録が欠けると
  prodリリースが止まる。記録の書き込みが失敗した場合の扱いを決める必要がある（未決定）。
- 手動実行の入力値（commit SHA、チケットID）を人間が指定するため、指定ミスの余地が残る。
  入力値の妥当性検証をCD側で行う必要がある。

## 見直しの契機

- デプロイ頻度を上げる要求が出て、承認ゲートがボトルネックになったとき
- devへのデプロイで事故が起きたとき（devにも最小限のゲートを入れるか再検討）

## 補足（2026-10-10 環境の定義を明確化して修正）

### 修正1: 理由の記述が目的と合っていなかった

当初「環境ごとにブランチが進んだり遅れたりする状態がバラツキの原因」と書いたが、
これは**環境間**のバラツキの話であり、本基盤の目的（**アプリチーム間**のバラツキを
なくすこと）の論証としては不適切だった。正しくは次のとおり。

> ブランチ戦略をチームごとに選べる状態にすると、それ自体がチーム間のバラツキになる。
> したがってブランチ戦略は**プラットフォーム全体で1つに固定し、アプリごとに
> 設定できないようにする**。

結論（trunk-based + 手動リリース）は変わらないが、根拠はこちらである。
この点は要件定義書のFR-05として要件化した。

### 修正2: devはサンドボックスであり、昇格チェーンに含まれない

当初devを「mainの最新が入っている統合環境」として扱っていたが、
実際の役割は「**開発者が自由にデプロイして動作確認するサンドボックス**」である。

この違いにより、当初挙げていた懸念の多くが解消する。

| 当初の懸念 | サンドボックスとして定義した場合 |
|---|---|
| devへ複数ブランチをデプロイすると競合する | 問題にならない。後から入れた方が勝つのはサンドボックスの当然の挙動 |
| devのドリフト検知が差分だらけになる | **devをドリフト検知の対象外にすればよい**（ADR-0012の補足） |
| ADR-0005（1回ビルドして昇格）が破綻する | 破綻しない。devを昇格チェーンから外せばよい |

### 修正3: mainマージ時にdevへ自動デプロイしない

mainマージ時に行うのは**成果物のビルドとECRへのpush、digestの記録まで**とし、
デプロイはしない。

理由は2つ。

1. devはサンドボックスなので、自動デプロイすると**開発者の検証を無断で上書きする**
2. 自動デプロイすると、devに「お試しのデプロイ」と「正規の成果物のデプロイ」が
   混在し、「今のdevはどちらか」という問いが常に発生する

これにより昇格チェーンは **`main → stage → prod`** となり、devは完全に
チェーン外のサンドボックスになる。

### 修正4: devへのデプロイは手動実行

ブランチ名の規則（`feature/*` のpushで自動デプロイ）も検討したが、手動実行を採用した。

| 案 | 却下理由 |
|---|---|
| ブランチ名規則でのpush自動デプロイ | 軽微なpushごとにデプロイが走る。意図しないデプロイと待ち時間が発生する |
| PRラベル | ラベル運用の規律に依存する |

手動実行（`workflow_dispatch`）なら「誰が何をdevに出したか」が明示的に残る。

ただし**サンドボックスであっても状態が分からないと調査ができない**ため、
devへのデプロイもDynamoDBに記録し、`concurrency` でアプリ単位に直列化する。
