# ADR-0005: 成果物は1回だけビルドし、環境差は実行時に注入する

- **状態:** 承認済み
- **日付:** 2026-09-30
- **関連:** ADR-0004, ADR-0007, ADR-0010

## 背景

環境ごとにビルドを分ける運用は珍しくない。Gradleで `-Pprofile=dev` / `-Pprofile=prod` のように
プロファイルを切り替えてビルドする構成は実際に存在する。

一方で、本基盤の目的は「各アプリチームごとのデプロイ精度のバラツキをなくす」こと。
環境別ビルドはこの目的と衝突する可能性があるため、方針を明確にする必要があった。

## 決定

### 原則

**ビルドは1回だけ行い、同一の成果物を昇格させる。**

昇格チェーンは **`main → stage → prod`**。devはサンドボックスであり昇格チェーンに
含まれない（環境の定義は[要件定義書 4.1](../requirements.md#41-環境)を参照）。
devへは任意のブランチを手動デプロイできるため、devで動いたことは
prodで動くことの根拠にならない。根拠になるのはstageでの確認である。

環境ごとの差分は、設定を3種類に分類して扱う。

| 種類 | 例 | 扱い方 |
|---|---|---|
| ① 実行時に決まる設定 | 接続先URL、DB名、ログレベル、機能フラグ、タイムアウト値 | 環境変数 / SSM Parameter Storeから実行時に注入。成果物には含めない |
| ② 秘密情報 | DBパスワード、APIキー | Secrets Manager / SSM SecureString。成果物には絶対に含めない |
| ③ ビルド時に決まるもの | フロントSPAのバンドルに埋め込む値 | 後述の例外規定 |

- 成果物の識別子は **commit SHA と image digest（Lambdaはzipのハッシュ）** とする。
- ECRのイメージタグはcommit SHAとし、デプロイ時はタグではなく **digestで指定する**
  （タグは後から付け替えられるため、digestでなければ同一性が保証されない）。

### アプリごとの具体策

- **appA（Java / ECS）:** Spring Profileは実行時選択なので、そのまま原則に乗る。
  1つのjarに全プロファイルの設定を同梱し、ECSタスク定義（環境ごとにTerraformが生成）で
  `SPRING_PROFILES_ACTIVE` を渡す。秘密情報はタスク定義の `secrets` でSecrets Managerから注入。
- **appB（Python / Lambda）:** 同一のzipを3環境にデプロイし、Lambdaの環境変数で切り替える。
- **appC（TypeScript / ECS）:** サーバーサイドであれば `process.env` で実行時に読む。
  ブラウザに配る画面を含み `VITE_` / `NEXT_PUBLIC_` 相当の値をバンドルに埋め込む場合のみ、
  ③の例外に該当する。

### 例外規定

③に該当する場合、まず「バンドルに焼かない」方法を検討する。

- コンテナ起動時に `config.js` を生成して配信する
- 起動後に `/api/config` を取得する

それでも不可能な場合のみ、次の条件付きで環境別ビルドを許可する。

1. `.platform/app.yaml` に `build_per_env: true` と明記し、理由をコメントで残す
   （黙って例外にはできない構造にする）
2. **同一のcommit SHAからビルドする**
3. リリースの識別子を「1つのdigest」ではなく **commit SHA + 環境ごとのdigestの一覧** として
   DynamoDBに記録する（ADR-0010）
4. prodビルドの実行条件として、**同じcommit SHAがstageで成功していること**をCDで検証する

## 理由

- **環境別ビルドは「stageで検証したものと、prodに出るものが別物」という状態を作る。**
  stageでの検証が「そのもの」の検証にならず、検証の意味が弱まる。
- **prodビルドだけが失敗する事故がリリース当日に発覚する。** 環境別ビルドでは、prod用の
  ビルド経路がリリース直前に初めて実行されることになる。
- **①②が成果物に焼かれていることが環境別ビルドの原因であり、そこを外に出せば不要になる。**
  Spring Profileがそもそも実行時選択であるように、多くのフレームワークは既にこれを
  前提に設計されている。ビルド時に分けているのは、多くの場合が習慣による。
- 例外を禁止せず「宣言させる」形にしたのは、禁止すると宣言せずに迂回されるため。
  例外の存在が `app.yaml` から可視化されていれば、後から解消の対象として追える。

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| 環境ごとにビルドする（現状の慣習を許容） | dev/stage/prodで別々にビルド | 検証したものと出るものが別物になる。目的と正面衝突する |
| 環境別ビルドを完全に禁止 | 例外を認めない | バンドル埋め込みが避けられないケースで迂回されるか、基盤に乗らなくなる |
| イメージタグで昇格を管理 | `stage` / `prod` タグを付け替える | タグは可変なので同一性が保証されない。digestで管理する |

## 結果とトレードオフ

**得たもの**

- stageでの検証結果がprodに出るものに対する検証として成立する
- ビルド回数が3分の1になり、CI時間とコストが減る
- リリース対象が「digest」という一意な値で表現でき、記録・追跡が単純になる

**諦めたもの・新たな負担**

- **既存アプリの移行に作業が必要。** 設定をビルド時から実行時に移す改修は、アプリ側の
  対応が前提になる。基盤側だけでは完結しない。
- **例外（`build_per_env: true`）を許したため、基盤内に2つの経路が存在する。** 例外側の
  ワークフロー・記録形式・検証処理を別に用意する必要があり、実装量と保守対象が増える。
- 設定の注入先が増える（環境変数、SSM、Secrets Manager）ため、アプリ起動時の
  設定解決が失敗したときの調査経路が複雑になる。

## 見直しの契機

- `build_per_env: true` のアプリが増え、例外が主流になってしまったとき
  → 例外側を正規の経路として作り直すか、フロント配信方式そのものを見直す
- digestベースの昇格で運用上の不都合が出たとき
