# ADR-0009: レポートと実行ログはprivate S3に保存する

- **状態:** 承認済み
- **日付:** 2026-09-30
- **関連:** ADR-0002, ADR-0008

## 背景

要件は「静的解析・脆弱性診断の結果をレポートとしてファイル出力し、CI/CD時のログとともに
S3に格納する」こと。

ここで2つの技術的制約がある。

1. **GitHub Actionsの実行ログは、実行中のジョブからは取得できない。** ジョブが完了するまで
   ログは確定しないため、同一の実行内でログ全体をS3へ上げることはできない。
2. **publicリポジトリでは、実行ログもArtifactも誰でも閲覧・ダウンロードできる（ADR-0002）。**
   レポートやplanの内容にARNやリソース名が含まれるため、Artifactに置くと公開されてしまう。

## 決定

### 保存先と構造

**専用のprivate S3バケット**に格納する。パブリックアクセスは全ブロック、暗号化必須、
バージョニング有効。

```
s3://<reports-bucket>/
  <service>/<app>/<ci|dev|stage|prod>/<commit_sha>/<run_id>/
    ├── reports/
    │   ├── semgrep.sarif
    │   ├── trivy-fs.sarif
    │   ├── trivy-image.sarif
    │   ├── trivy-config.sarif
    │   ├── gitleaks.sarif
    │   ├── lint.sarif
    │   └── summary.json      # ゲート判定の結果
    ├── terraform/
    │   ├── plan.txt
    │   └── plan.json
    └── logs/
        └── workflow-logs.zip
```

### ログの収集方法

**`workflow_run`（completed）をトリガーとする別ワークフローで、GitHub APIから
ログのzipを取得してS3へアップロードする。**

```
CI本体（完了）→ workflow_run イベント → collect-logs.yml
                                        → APIでログzipを取得 → S3へ
```

### publicリポジトリ対応

- **Artifactにはレポート・plan・ログを一切置かない。**
- **PRコメントには要約のみを載せる。** 件数、ゲート判定結果、S3へのコンソールリンク。
  plan全文やSARIFの詳細は載せない。
- PRコメントの生成時に、ARN・アカウントID・バケット名のパターンを伏せるフィルタを通す
  （マスク漏れに対する二重の保険）。

### 保持期間

- レポート・plan: 400日（監査を想定）
- ログ: 90日
- ライフサイクルルールで自動削除する。Object Lockは実験では設定しない。

## 理由

- **private S3に置く以外の選択肢がない。** publicリポジトリのArtifactは第三者が
  ダウンロードできるため、レポートの置き場所として使えない。
- **ログ収集を別ワークフローにするのは、GitHub Actionsの仕様上それしか方法がないため。**
  実行中のジョブが自分の完全なログを取得する手段は提供されていない。
  各ステップの出力を個別にファイル化する方法もあるが、ステップの追加漏れが発生し、
  「ログとともに格納」という要件を確実に満たせない。
- **キーにcommit SHAを含めるのは、成果物とレポートを対応付けるため。** stage/prodのCDが
  「このcommit SHAのCI結果」を参照する必要がある（ADR-0008）。run_idだけでは引けない。
- **PRコメントを要約に絞るのは利便性を犠牲にした判断。** plan全文をコメントに出す方が
  レビューしやすいが、publicリポジトリではその内容が公開される。
- 保持期間を400日にしたのは、年1回の監査サイクルを1周カバーできる長さとして。

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| Artifactに保存 | Actionsの標準機能 | publicリポジトリでは誰でもダウンロードできる |
| 各ステップの出力を個別にファイル化 | `tee` でファイルに落とす | ステップ追加時の漏れが発生する。要件を確実に満たせない |
| CloudWatch Logsに集約 | ログ基盤に寄せる | レポートファイルの置き場所としては不適。S3との二重管理になる |
| plan全文をPRコメントに出す | レビュー性を優先 | 機密が公開される |
| Object Lockで改変不可にする | 監査要件を厳格に | 実験段階では削除できない状態が運用の妨げになる。実務移行時に検討 |

## 結果とトレードオフ

**得たもの**

- レポート・plan・ログが単一の構造で集約され、commit SHAで横断的に引ける
- publicリポジトリでも機密が公開されない

**諦めたもの・新たな負担**

- **ログ収集が別ワークフローになるため、CI本体の成否とログ保存の成否が分離する。**
  ログ収集だけが失敗した場合、CI自体は成功しているのでログが欠落したことに気づきにくい。
  収集失敗時のSlack通知が必要（未実装）。
- **PRのレビュー体験が落ちる。** plan内容を確認するにはS3を見に行く必要があり、
  PR上で完結しない。
- **レポートを見るためにAWSコンソールへのアクセス権が必要になる。** 開発者がAWSの
  権限を持たない場合、レポートを閲覧できない。閲覧用の経路（署名付きURLの発行など）が
  別途必要になる可能性がある。
- S3のストレージコストとライフサイクル管理が発生する（量としては小さい）。

## 見直しの契機

- privateリポジトリに移行したとき（ADR-0002） → Artifactやplanコメントを使えるようになり、
  PRのレビュー体験を戻せる
- レポートの閲覧が実際に運用の妨げになったとき → 閲覧用の経路を用意する
- 監査要件が明確になったとき → Object Lockと保持期間を見直す
