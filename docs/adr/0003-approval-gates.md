# ADR-0003: 承認ゲートをGitHub Environmentsで実装する

- **状態:** 承認済み
- **日付:** 2026-09-30
- **関連:** ADR-0002, ADR-0010, ADR-0011, ADR-0015

## 背景

環境ごとに異なる段数の承認ゲートを設ける要件がある。

- dev: 承認なし
- stage: 1段階
- prod: 3段階

加えて、各ゲートには承認者のペルソナを設定し、承認タイミングでSlack通知を行い、
承認可否の状態を記録したい。

実験環境の制約は、個人アカウント・Free plan・publicリポジトリ（ADR-0002）・
使えるGitHubアカウントは1個・Slackはincoming webhookのみ（ADR-0015）。

## 決定

**承認判定の正本はGitHub Environmentsの Required reviewers とする。**

- 承認段数に応じて環境を作り、CDのジョブを直列につなぐ。

  | 環境名 | 用途 | 承認者ペルソナ |
  |---|---|---|
  | `dev` | dev環境デプロイ | なし |
  | `stage` | stage環境デプロイ | dev_lead |
  | `prod-approval-1` | prod 1段目 | dev_lead |
  | `prod-approval-2` | prod 2段目 | qa_po |
  | `prod-approval-3` | prod 3段目 | sre |
  | `prod` | prod環境デプロイ実行 | なし（3段通過後） |
  | `prod-emergency` | 緊急リリース（ADR-0011） | sre |

- **ペルソナと実アカウントの対応は `platform-cicd/config/approvers.yaml` で管理する。**
  Environments側の設定はこのファイルを正として反映する。

  ```yaml
  personas:
    dev_lead: { github: [moonlight4617], slack: [U01ABCDEF] }
    qa_po:    { github: [moonlight4617], slack: [U01ABCDEF] }  # 将来差し替え
    sre:      { github: [moonlight4617], slack: [U01ABCDEF] }  # 将来差し替え
  gates:
    stage:          [dev_lead]
    prod:           [dev_lead, qa_po, sre]
    prod_emergency: [sre]
  ```

- **各承認ジョブの直前にSlack通知ジョブを置く。** 対象ペルソナのSlack IDでメンションし、
  承認画面のURL・対象アプリ・環境・commit SHA・チケットIDを送る（ADR-0015）。
- **DynamoDBは承認判定には使わず、記録・参照用途に限定する（ADR-0010）。**
  誰がいつどの段を承認したかの監査記録、およびprod前のstage成功確認に使う。
- Environmentsの「自分のデプロイを自分でレビューさせない」設定は **OFF** にする
  （承認者が1アカウントのため、ONだと誰も承認できなくなる）。

## 理由

- **判定の正本を1つに保てる。** GitHubとDynamoDBの両方を正本にすると、片方だけ更新された
  状態（食い違い）が必ず発生する。判定はGitHub、記録はDynamoDBと役割を分ければ、
  食い違いが原理的に起きない。
- **承認画面・履歴・通知・タイムアウト（最大30日）がすべて標準機能で揃う。** 自作すると
  これらを全部作ることになり、実験の主題（プラットフォームとしての一貫性）から逸れる。
- **段数の表現を「環境の直列」にすると、段ごとに承認者を完全に分離できる。** 1つの環境に
  3人を登録する方式では、GitHubの仕様上「登録者のうち誰か1人の承認」で通過してしまい、
  3段階の承認にならない。
- ペルソナを設定ファイルに外出しすることで、承認者が1人しかいない実験段階でも
  **意図した承認体制を表現でき**、実アカウントの割り当てだけ後から差し替えられる。

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| Slackのボタンで承認 | Slack App + API Gateway + Lambda + DynamoDB | Slackはincoming webhookのみという制約（ADR-0015）。Slack Appの作成・権限申請が実験の範囲を超える |
| GitHub Issueコメントで承認 | `/approve gate1` をワークフローがポーリング | 待機中もActions時間を消費。publicリポジトリでは第三者がコメントできるため、権限判定を自作する必要がある |
| DynamoDBを承認の正本にする | CLIで承認を書き込み、ジョブがポーリング | 正本が2つになる問題。加えてポーリングのコスト |
| 1つのprod環境に3人を登録 | 承認者を3名登録 | 1人の承認で通過するため3段階にならない |
| カスタム保護ルール（GitHub App） | 外部システムに判定を委譲 | 自作の複雑さに見合わない。privateリポジトリではEnterpriseも必要 |

## 結果とトレードオフ

**得たもの**

- 標準機能のみで多段承認が成立し、履歴もGitHub上に残る
- ペルソナ定義が構成管理されるため、承認体制がコードとしてレビュー可能

**諦めたもの・新たな負担**

- **承認者が1アカウントのため「別人が承認する」検証ができない。** 3段すべてを同一人物が
  承認する形になり、権限分離が実際に効くかは未検証のまま残る。また自己レビュー禁止設定を
  OFFにする必要があり、実務では必ずONにすべき設定を実験では無効化している。
  この差分は実務移行時の確認項目。
- **Environmentsの設定がGitHub UI上の状態として存在し、コード管理されない。**
  `approvers.yaml` を正としつつ、実際の反映は手作業になる。将来的にはTerraformの
  GitHub providerで環境設定も宣言的に管理したい（未着手）。
- 承認環境が7つに増えるため、リポジトリごとの初期設定項目が多い（ADR-0001のトレードオフと連動）。

## 見直しの契機

- 承認者として使えるアカウントが複数になったとき → 自己レビュー禁止をONにし、
  ペルソナに実アカウントを割り当てる
- Slack Appが使えるようになったとき → 通知だけでなく承認操作もSlackに寄せるか再検討
- Environments設定の手作業が事故につながったとき → GitHub providerでの宣言的管理へ
