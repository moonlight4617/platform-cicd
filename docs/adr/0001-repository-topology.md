# ADR-0001: リポジトリ構成を1アプリ1リポジトリ + 中央リポジトリにする

- **状態:** 承認済み
- **日付:** 2026-09-30
- **関連:** ADR-0014

## 背景

社内には複数のサービスがあり、各サービスは複数のアプリを持つ。実験対象は次の構成。

```
serviceA
├── appA   (Java, ECS)
├── appB   (Python, Lambda)
├── appC   (TypeScript, ECS)
└── infraA (appA/B/Cで共通の資材)
serviceB
└── appD   (Java, ECS)
```

当初「モノレポ構成で1アプリごとに1リポジトリ」という相反する前提が置かれていたため、
どちらなのかを確定させる必要があった。また、共通CI/CDを「どうやって各アプリに配るか」が
この構成に強く依存する。

## 決定

- **1アプリ = 1リポジトリ**とする（サービス単位のモノレポにはしない）。
- CI/CDの実装は中央リポジトリ `platform-cicd` に集約し、各アプリはGitHub Actionsの
  再利用可能ワークフロー（`workflow_call`）として呼び出す。
- 各アプリリポジトリに置くのは以下のみとする。
  - 呼び出しだけを書いた薄いワークフロー（10行程度）
  - アプリの種別を宣言する設定ファイル `.platform/app.yaml`
  - アプリ固有のTerraform（ECSサービス、Lambda関数など）
  - アプリのソースコード
- 共通ワークフローの参照はタグで固定する（`moonlight4617/platform-cicd/.github/workflows/ci.yml@v1`）。
- 実験中はローカルの1ディレクトリ配下にリポジトリ相当のフォルダを並べて開発し、
  最終的に個別のGitHubリポジトリとしてpushする。

```
sample_cicd/
├── platform-cicd/    # 共通ワークフロー、composite action、設定
├── platform-infra/   # S3, DynamoDB, OIDC, IAMロール, VPC, ALB
├── serviceA-infra/   # infraA
├── serviceA-appA/    # Java / ECS
├── serviceA-appB/    # Python / Lambda
└── serviceA-appC/    # TypeScript / ECS
```

`.platform/app.yaml` の例:

```yaml
service: serviceA
app: appA
runtime: java
deploy: ecs
build_per_env: false   # ADR-0005 の例外規定
```

## 理由

- **「アプリ側が処理を書けない」形にできる。** 目的はデプロイ精度のバラツキをなくすこと。
  各チームがワークフローを自由に書ける状態では、書き方の差がそのまま精度の差になる。
  アプリ側の記述を宣言だけに絞れば、実装差が生まれる余地がなくなる。
- **モノレポだと変更検知の実装が必要になる。** どのアプリが変わったかをパス差分から
  判定する処理が常に挟まり、判定漏れが事故につながる。1アプリ1リポジトリなら不要。
- **権限と承認者をリポジトリ単位で分離できる。** 承認ゲート（ADR-0003）はEnvironmentsで
  設定するため、リポジトリが分かれている方が素直に表現できる。
- **タグ固定により、基盤側の変更が全アプリへ一斉波及するのを防げる。** 基盤の変更で
  全アプリのCIが同時に壊れる事態は共通化の最大のリスクなので、仕組みで防ぐ。

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| サービス単位のモノレポ | serviceA配下に全アプリを置く | 変更検知の実装が必須になり判定漏れが事故化する。承認者の分離も複雑になる |
| 各リポジトリにワークフローをコピー | テンプレートを配布し各チームが保持 | コピーが劣化・分岐し、バラツキをなくす目的に反する |
| ブランチ参照（`@main`）で共通化 | 常に最新を参照 | 基盤の変更が全アプリに即時波及する |

## 結果とトレードオフ

**得たもの**

- アプリ側の記述量が最小化され、実装差が生まれない
- 基盤側の変更を段階的に展開できる

**諦めたもの・新たな負担**

- **リポジトリ数が増える。** アプリが増えるたびにリポジトリ作成・Secrets設定・
  Environments設定が必要になる。将来的にはリポジトリ作成の自動化（テンプレートリポジトリ
  またはTerraformのGitHub provider）が必要になる可能性がある。
- **共通ワークフローのバージョン管理が新たな運用作業になる。** `v1` タグの更新方針と、
  破壊的変更時の `v2` 移行手順を決める必要がある（未決定）。
- 複数アプリをまたぐ変更で、リポジトリ横断のアトミックなコミットができない。

## 見直しの契機

- 1サービス内のアプリ数が十数個規模になり、リポジトリ管理コストが変更検知の実装コストを
  上回ったとき
- アプリ間で密結合な同時変更が頻発するようになったとき
